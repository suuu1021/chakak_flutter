Subject: `/api/email/verify` 관련 최근 테스트 결과 및 요청 사항 종합 전달

안녕하세요, 서버 개발팀께.

`/api/email/verify` 엔드포인트와 관련하여 최근 저희 쪽에서 테스트했던 내용과 현재 상황, 그리고 이에 따른 요청 사항을 종합하여 다시 한번 전달드립니다.

**1. 최근 테스트 상황 요약 (서버 HTTP 200 응답 시 필드명 불일치 문제)**

*   저희 클라이언트는 "[서버팀 최종 공지] 클라이언트 API 최종 통합 안내 문서 (최종본)"에 명시된 대로, `/api/email/verify`의 성공 응답 본문에서 `data` 필드(boolean)로 성공 여부를, `message` 필드(String)로 메시지를 읽도록 코드를 구현하고 테스트했습니다.
*   테스트 결과, 서버로부터 HTTP 200 OK 응답을 성공적으로 수신했으나, 응답 본문이 다음과 같은 형식이었습니다:
    `{"status":200,"msg":"이메일 인증에 성공했습니다.","body":true}`
*   API 문서에는 `data`와 `message`로 명시되어 있으나, 실제 응답은 `body`와 `msg` 필드를 사용하고 있어, 클라이언트는 `data` 필드를 찾지 못해 서버의 성공 응답을 인증 실패로 잘못 해석하는 상황이 발생했습니다.

**2. 현재 클라이언트 상태 및 이전 문제점 지속 가능성**

*   위 테스트 이후, 저희 클라이언트 코드는 혼선을 피하기 위해 **API 최종 문서의 명세를 정확히 따르는 상태 (즉, `data` 및 `message` 필드를 기대하는 상태)로 유지**하고 있습니다.
*   따라서, 만약 서버가 계속해서 `/api/email/verify`의 성공(HTTP 200) 또는 일반적인 실패(HTTP 400) 응답에 대해 `body`, `msg` 필드를 사용한다면, 클라이언트는 이를 올바르게 처리하지 못하고 이전 테스트와 동일한 해석 오류를 겪게 될 것입니다.
*   또한, 만약 서버가 이전에 빈번히 발생했던 HTTP 500 오류 (`{"status":500,"msg":"존재하지 않는 이메일입니다.","body":null}`)를 다시 반환한다면, 이 문제의 근본적인 원인 해결 또한 여전히 필요한 상황입니다.

**3. 서버팀에 대한 요청 사항 (종합)**

원활한 회원가입 기능 구현을 위해 다음 사항들을 다시 한번 간곡히 요청드립니다.

*   **요청 1 (필드명 통일):** `/api/email/verify` 엔드포인트의 **모든 응답(HTTP 200 성공, HTTP 400 실패 등 모든 경우)에 대해, 응답 본문의 필드명을 "[서버팀 최종 공지] 클라이언트 API 최종 통합 안내 문서 (최종본)"에 명시된 대로 `data` (성공/실패 여부) 및 `message` (관련 메시지)로 통일**해주십시오. (예: 성공 시 `{"data": true, "message": "이메일 인증에 성공했습니다."}` / 실패 시 `{"data": false, "message": "인증 코드가 일치하지 않습니다."}`)

*   **요청 2 (HTTP 500 오류 근본 원인 해결):** 만약 HTTP 500 "존재하지 않는 이메일입니다." 오류가 다시 발생할 경우, 이는 이메일 인증 코드를 `EMAIL_VERIFICATION` 테이블에서 확인하기 전에 `user_account` 테이블을 먼저 참조하여 발생하는 문제로 강력히 추정되오니, **해당 로직을 수정하여 `EMAIL_VERIFICATION` 테이블을 우선적으로 검증하도록 변경**해주십시오.

지속적인 소통에도 불구하고 문제가 해결되지 않아 양 팀 모두 어려움을 겪고 있는 점 안타깝게 생각합니다. 부디 위 요청 사항들을 면밀히 검토해주시어, 클라이언트가 API 문서에 따라 안정적으로 서버와 통신할 수 있도록 조치해주시기를 부탁드립니다.
